01概览与 v3.1 修订

配套文件：schema.sql / gen_data.py / data.sql / v2_数据补全.sql，以及 MySQL-master 的 27 条分析脚本。

v3 的底子是「原地补全，不重建」：v2_数据补全.sql 用两个幂等存储过程（safe_add_col、insert_if_empty）给老库加列加表，跑第二遍也不会报错。这一版（v3.1）在 v3 基础上做了一次通读校对，改动如下：

改动内容
订正数据错误v3 原写「年龄均匀 1960~2005」有误。v2_数据补全.sql 第 56 行按 '19' || 70~98 生成，iDdate 实际是 1970–1998，快照日对应 17–46 岁。
SQL 别名规范化模板里的别名 sum 改为 trade_amt——和聚合函数同名，读起来容易看漏，部分客户端还会误高亮。逻辑与原脚本等价。
统一表数量口径v2 之后全库 32 张表（含同构副本与快照分片）。README 里的「15 张」是 v1 时期的说法，已过期。

陷阱扩到 14 条补「50 岁及以上分桶恒为 0」与「age_group 三个标签是空档」——两个都会让人误以为 SQL 写错。

04黄金组合

全库最高频的一条 WHERE。只记一条，就记这条。

golden_rule.sql
WHERE biztype IN (1, 3) AND inouttype = 1 AND `status` = 20

三个条件缺一不可：

  • 漏 biztype → 充值 / 提现（biztype = 4）被当成投资；
  • 漏 inouttype = 1 → 回款、提现混进投资额；
  • 漏 status = 20 → 失败单计入成交。

算钱时还有一条：交易总额是四列相加 amount + assetamount + bonusamount + couponamount，只取 amount 会漏掉点点宝余额与抵扣部分。

09字段字典 · 资金与持仓

这一组决定「钱怎么算」。回款、余额、收益分别落在不同的表。

account_inout 回款流水

biztype(1=优选回款) / inouttype(2=流出) / amount(回款总额) / profit(收益部分，本金 = amount − profit；v2 起无 NULL) / createtime。

ds_save_accountbal 余额快照

saveday(DATE) + asset(截至当日凌晨的余额)。「账户余额」脚本做的是存量 + 流量组合分析。

selfitem / da_selfitem 标的维度

id / itemtitle / totalperiods / annualrate(年化 %，5.5~12.8)。「新老用户交易区分」按 annualrate 判新手标。

account_selfitem / da_account_selfitem 持仓关系

accountid + itemid，用户与标的的多对多关系。

account_ddb_income 点点宝收益

accountid / amount(持有本金) / income(当期收益) / incomedate(DATE 收益归属日)。2015 年终汇总用它算平台累计收益。

account_selfitem_income 优选理财收益

accountid / itemid / income / incomedate。由持仓 × 标的年化推导（8% 持仓 × 20 个月）。供「2015 年终数据报告」「产品数据需求」的 sum(income) 使用；平台总收益 = ddb_income + 本表。

score_gain_stream 签到流水

accountid / status(1=成功) / createtime。「每日登录与签到」脚本同时对比 appopenlog 口径——「活跃指标必须声明口径」的现成教材。

14修正版 SQL 模板

画像交叉四连，可直接喂看板。相对原脚本只改了别名（sum → trade_amt）与注释，逻辑等价。

14.1 年龄交叉交易额 年龄现算版

age_cross.sql
SELECT 年龄段, count(*) AS 人数, sum(trade_amt) AS 交易额
FROM (
  SELECT CASE
           WHEN age < 20 THEN '20岁以下'
           WHEN age < 30 THEN '20-29岁'
           WHEN age < 40 THEN '30-39岁'
           WHEN age < 50 THEN '40-49岁'
           ELSE '50岁及以上'
         END AS 年龄段,
         trade_amt
  FROM (
    SELECT a.id,
           TIMESTAMPDIFF(YEAR, a.iDdate, '2016-01-11') AS age,  -- 派生指标现场计算
           b.trade_amt
    FROM da_ds_account_0111 a
    JOIN (SELECT accountid,
                 sum(amount+assetamount+bonusamount+couponamount) AS trade_amt
          FROM da_account_trade
          WHERE biztype IN (1,3) AND inouttype = 1 AND `status` = 20
          GROUP BY 1) b ON a.id = b.accountid
  ) t
) aaa
GROUP BY 1
ORDER BY FIELD(年龄段, '20岁以下', '20-29岁', '30-39岁', '40-49岁', '50岁及以上');

要点：年龄必须锚定快照日；GROUP BY 后用 ORDER BY FIELD 固定分桶顺序。偷懒版：直接 GROUP BY d.age_group（固化列）。

「50 岁及以上」这一桶恒为 0——iDdate 最早 1970 年，快照日最多 46 岁。看到空桶不是 SQL 写错。

15陷阱清单（14 条）

结果不对时先扫一遍这里——多数「SQL 写错了」其实是口径选错了。

  1. `status` 同名不同义：交易 20 / 券 0-1-2 / 拼团 3-4 / 签到 1。写 WHERE 前先回枚举表对表。
  2. 两张 channel 不同源：account.channel = 从哪来，account_trade.channel = 在哪成交。
  3. biztype=4 不是投资：算投资总额必须 biztype IN (1,3)。
  4. 四列相加才是交易总额：amount+assetamount+bonusamount+couponamount，漏 assetamount 会低估。
  5. v2 起别再用 commandid IS NULL 判渠道：改用 reg_source。
  6. youyu 的 id 与主站不通：不能直接 JOIN，只能各自聚合后合并。
  7. 回款要拆本息：account_inout 本金 = amount − profit。
  8. date() vs hour() 粒度：日报用 date(createtime)，时段分布用 hour(createtime)，混用会对不上数。
  9. 业务不适用 NULL ≠ 缺失：commandid（渠道用户）、itemid（充提行）故意为 NULL，不要「修复」。
  10. 原脚本 bug ①：用户画像 #8「地区交叉」开头有两行 SELECT，删掉第一行才能跑。
  11. 原脚本 bug ②：星座 CASE 里摩羯座写 BETWEEN '12-22' AND '01-19'，字符串比较永假（摩羯座永远空组），必须拆成 '12-22'~'12-31' 与 '01-01'~'01-19' 两段。
  12. 年龄是派生指标：库里只有 iDdate 原子字段；快照表里的 age 是按 2016-01-11 固化的，换时点须现算。
  13. 「50 岁及以上」分桶恒为 0v3.1：iDdate 区间 1970–1998，快照日最大 46 岁。空桶不代表数据坏了。
  14. age_group 的三个标签是空档v3.1：CASE 里写了「60前 / 60后 / 00后」，但数据只落在 70后~90后；按 age_group 出图会少三档。

18附录 A · v2 补全说明

补全脚本做了什么、怎么验收、还留着什么坑。

  • 脚本：v2_数据补全.sql（全量，幂等）/ v2_补全_增量版.sql（第 4 节起，适合 1~3 节已跑过的库）。
